# Project AYBS — ステージシーンデータ設計

作成：2026-11-20。元資料「仕様：座標系とステージデータ構造.md」からデータ構造・引継ぎを分割。

本書は戦闘シーン共通のデータ設計。B24の個別ステージ値は「定義：B24戦役ステージデータ.md」、座標・領域・マップ運動は元資料を参照する。C#は未実装の構造案であり、未決定フィールドを自動確定しない。

## 1. ステージデータの階層

```text
StageData                         ステージ識別・設定の親データ
├─ PlanetStageSettings            惑星半径・位相・距離係数
├─ PlayerSpawnData                プレイヤー初期座標・向き
└─ EnemyFormationData             敵艦の構成・配置データ
   └─ EnemyShipData[]             敵艦1隻ごとの建造パラメータ・装備性能・旗艦判定・座標
```

`EnemyFormationData` は複数の `EnemyShipData` を保持する編成データとして整理する。

道中戦闘の敵部隊も `EnemyFormationData` を保持する。戦闘開始時の敵艦の相対座標は編成データに固定し、恒星系マップ上の接近方向に合わせた編成の回転は行わない。

### PlayerSpawnData：プレイヤー初期配置

| フィールド | 型 | 内容 |
|---|---|---|
| position | Vector2 | 戦闘領域内の初期座標 |
| rotationDeg | float | 初期の向き（度） |

初速はデータに持たせない。StageDataに `playerSpawn` として保持する整理案とする。

生成直後のプレイヤー初速は0 U/s。既存追記に従い敵艦も速度0で生成し、その後に操艦AIを開始する。

道中戦闘ではプレイヤーの開始時の向きを右向きに固定する。マップ上の進行方向から開始時の向きを決めない。


## 2. EnemyShipData：敵艦1隻の定義

| フィールド | 型 | 内容 |
|---|---|---|
| weaponIDs | int[7] | 兵装カタログID配列（性能はカタログを参照） |
| weaponCounts | int[7] | 各兵装の数 |
| turretHP | int | 砲塔区画HP |
| armorSettings_Basic | ArmorSetting | Basicの装甲設定 |
| armorSettings_ERA | ArmorSetting | ERAの装甲設定 |
| armorSettings_AEM | ArmorSetting | AEM（対電磁処理装甲）の装甲設定 |
| coreHPSettingID | int | コアHP設定ID |
| seed | int | 艦体生成シード |
| EquipmentPerformanceValues | string | 設備性能。項目の対応・読み出しは施設設計メモ参照 |
| isFlagship | bool | 旗艦フラグ。編成内に複数の旗艦を設定できる |
| position | Vector2 | 戦闘領域内の初期座標 |

### 装甲設定の構造

`ArmorSetting` の1要素は次の3項目。

| フィールド | 型 | 内容 |
|---|---|---|
| armorCount | int | 装甲区画の数 |
| hpSettingID | int | HPプリセットID |
| defenseThicknessSettingID | int | 迎撃力・装甲厚の組の設定ID |

現時点の装甲プリセットは以下のとおり。

| 設定ID | HP | 迎撃力 | 装甲厚 |
|---|---|---|---|
| 0 | 10 | 0.1 | 25 |
| 1 | 50 | 0.12 | 50 |
| 2 | 100 | 0.15 | 100 |
| 3 | 150 | 0.2 | 200 |
| 4 | 200 | 0.25 | 300 |

HP設定IDと迎撃力・装甲厚設定IDは独立して選択する。IDは「シーン設計1：艦設計システム.txt」の表に対応する。

装甲設定はBasic・ERA・AEM（対電磁処理装甲）の個別フィールドで保持する。各フィールドは共通の `ArmorSetting` 型を使用し、フィールド名で装甲種類を識別する。

### コアHPプリセット

プリセット値は次の11種類とする。

```text
500 / 1000 / 2000 / 5000 / 10000 / 15000 /
20000 / 25000 / 30000 / 40000 / 50000
```

`coreHPSettingID` は上記の順に0～10を割り当てる。HPと機動性能補正は「シーン設計1：艦設計システム.txt」を参照する。

### 設備性能の保存

現行設備一覧・MVP値・実数の0.0000形式による文字列保存は「仕様：施設設計.md」を参照する。ステージデータとの接続・ID割当は同メモで管理する。

### AI設定の追加方針（11月15日決定）

- enum AITypeで操艦AI種別を定義し、AIType major（主AI）とAIType fallback（代替AI）を持つ。
- 7種の運動仕様は「仕様メモ：戦闘AI仕様メモ.txt」を参照。enumの名称・IDは未確定。
- 攻撃対象・護衛対象はGameObject配列で定義する。護衛対象は同陣営に限定せず、敵艦の護衛も可能とする。
- 固定周回中心、周回半径などの具体的な型と、照準カテゴリ別重み5値の保存先は未決定。
- 以下のC#案にはこれらの追加項目と設備保存の接続は未反映。完成したデータ定義として使用しない。

### プレイヤー艦の建造保存・生成

建造シーンでプレイヤーの次の項目を保存する。ステージ開始処理は保存済みデータを読み出してプレイヤー艦を生成し、PlayerSpawnDataの座標・向きを適用する。初速は0。

| フィールド | 型 |
|---|---|
| weaponIDs | int[7] |
| weaponCounts | int[7] |
| turretHP | int |
| armorSettings_Basic | ArmorSetting |
| armorSettings_ERA | ArmorSetting |
| armorSettings_AEM | ArmorSetting |
| coreHPSettingID | int |
| seed | int |
| EquipmentPerformanceValues | string |
| equippedEquipmentInstanceIDs（名称案） | 設備個体IDの配列。要素型は未決定 |

装備中IDは設備種別IDとは別の、所持する設備個体への参照として保存する。兵装はweaponIDsでカタログIDを、weaponCountsで数量を保存する。設備個体IDの採番・型・性能保存値との照合方法は未決定。

入力不備はエラーとする。既存の惑星侵入禁止領域と敵艦初期配置の重複検出と同じ方針で検証し、不備を黙って補完しない。保存ファイルの場所・読み書き方式は別途定義する。

### 建造中データの保存条件

- 目安区画数・装甲区画数・武装区画数はプレイヤーが指定する。
- `目安区画数 == 装甲区画数 + 砲塔区画数` を恒星系マップへの遷移・保存条件とする。ここで砲塔区画数は武装区画数を指す。この式にコア用の+1は加えない。
- 不一致なら設計中データを保存せず、以前の保存済み設計を維持する。
- 一致し、入力検証を通過した状態で「恒星系マップへ戻る」を押した際にのみ設計を保存して遷移する。不一致では戻れない。
- 条件の成立／不成立が切り替わった時にボタンの状態を更新する。不成立時は半透明・操作不可、成立時は通常表示・操作可能とする。半透明時の具体的な透明度は未決定。
- 保存済み設計と編集中データを分離し、戦闘で使用するのは保存済み設計とする。
- 入力数の整合と、形状生成後の実区画数の過不足は区別する。生成結果側の扱いは接続事項として残す。

### 対象・旗艦・撤退艦の管理

| 項目 | 定義 |
|---|---|
| 攻撃対象 | GameObject配列 |
| 護衛対象 | GameObject配列。敵艦も指定可能 |
| 旗艦一覧 | GameObject配列で管理する案。撤退判定で残存旗艦を参照する |
| 撤退艦一覧 | 戦闘領域から離脱した艦を保持する配列 |

`List<GameObject, float>`はC#のListとしては定義できない。組にする場合は次のような要素型を用いる（表現例。float値は保存時のコアHP割合）。

```csharp
[Serializable]
public class ShipValueEntry
{
    public GameObject ship;
    public float coreHpRatio;
}
// List<ShipValueEntry> または ShipValueEntry[]
```

GameObject配列は戦闘中の実体参照として扱う。シーンを越えて撤退艦を再生成するための建造データ・損傷情報は、実体が消失する前に保持する必要がある。損傷の保存値は `コア現在HP / コア最大HP`。各区画の個別損傷は保存せず、ステージデータから艦を再生成した後、コアを含む全区画の生成直後HPにこの割合を乗算する。最大HP自体は変更しない。元のステージ艦データの識別・参照方法は別途定義する。ScriptableObjectのStageDataと生成後のGameObject配列を結び付ける方法も別途定義する。

## 3. Unity C#データ構造案

実装の土台となるデータ定義案。

```csharp
using System;
using UnityEngine;

[Serializable]
public class PlanetStageSettings
{
    public float radiusU = 100000f;
    public float phaseDeg;
    public float distanceFactor = 1f;
}

[Serializable]
public struct PlayerSpawnData
{
    // 初速はデータに持たせない
    public Vector2 position;
    // 道中戦闘の開始時は右向きに固定
    public float rotationDeg;
}

[Serializable]
public class ArmorSetting
{
    public int armorCount;
    public int hpSettingID;
    public int defenseThicknessSettingID;
}

[Serializable]
public class PlayerShipBuildData
{
    // 兵装（それぞれ長さ7）
    public int[] weaponIDs = new int[7];
    public int[] weaponCounts = new int[7];

    // 艦体設計
    public int turretHP;
    // 装甲種類ごとの個別設定
    public ArmorSetting armorSettings_Basic;
    public ArmorSetting armorSettings_ERA;
    public ArmorSetting armorSettings_AEM;
    public int coreHPSettingID;
    public int seed;

    // 設備（文字列の読み出し・IDとの接続は施設設計メモを参照）
    public string EquipmentPerformanceValues;

}

[Serializable]
public class EnemyShipData : PlayerShipBuildData
{
    // 旗艦配列への移行は提案段階。生成時の旗艦指定を保持する。
    public bool isFlagship;
    public Vector2 position;
}

[Serializable]
public class EnemyFormationData
{
    public EnemyShipData[] ships;
}

[CreateAssetMenu(
    fileName = "StageData",
    menuName = "Warship/Stage Data"
)]
public class StageData : ScriptableObject
{
    public string stageID;
    public PlanetStageSettings planet;
    public PlayerSpawnData playerSpawn;
    public EnemyFormationData enemyFormation;
    [Range(0f, 1f)] public float retreatHpRatioThreshold;
    public int remainingFlagshipThreshold;
    public Vector2 retreatDirection;
}
```

C#の `int[]` は宣言だけでは長さが固定されないため、兵装7要素という制約は、後で `OnValidate` などによって保証する必要がある。設備側は「仕様：施設設計.md」の正式設備と個体性能文字列の接続を定義してから検証する。

Unityの `Vector2` は単精度なので、戦闘領域内のローカル座標に使用し、恒星系全体の位置は従来どおり倍精度で管理する構成とする。

## 4. シーン間の情報受け渡し

恒星系マップから戦闘領域へ、艦船や砲弾の軌道を厳密に変換する必要はない。戦闘領域では位置・速度を独立して管理する。戦闘座標の単位は引き続きUとし、現実のメートルには固定しない。

受け渡す論理情報の候補は以下。具体的に何を引き継ぐかは未確定。

- 接敵位置
- 参加部隊
- 艦の状態
- 戦闘結果

例えば、第5惑星付近で敵哨戒部隊が接敵範囲に入ったら、その部隊の情報を渡して道中戦闘を開始し、終了後にプレイヤーと敵部隊の状態を恒星系マップへ反映する。

道中戦闘の相対配置は敵部隊の編成データに固定し、編成を回転させない。プレイヤーの開始時の向きは右向きに固定する。マップ上の会合点の計算と、戦闘領域内の固定配置は別に扱う。

戦闘領域内で編成の相対座標の基準点をどこに置くか、および主戦闘での接近方向の反映は未指定。

### 戦闘中の恒星系マップ航行（確定）

戦闘中は恒星系マップの航行を停止し、戦闘終了後に同じ接敵地点から再開する。戦闘中の経過時間によってマップ上の航行位置を進める処理は行わない。

### 敵艦の撤退（今回決定）

StageDataに撤退割合閾値r（0～1）、残存旗艦数k（整数）、撤退方向を指定する。

撤退開始条件は、残存旗艦集合Fについて次の両方を満たすこと。

```text
Fの要素数 <= k
かつ
F内の少なくとも1艦が 現在HP <= 最大HP × r
```

HP割合で表す場合は `現在HP / 最大HP <= r`。割合とHP量を混同しない。旗艦が0艦の場合は「少なくとも1艦」が成立しないため、この式では撤退開始しない。全滅時の終了判定は別に扱う。

1. 撤退開始後、すべての敵艦は指定方向へ回頭して全速移動する。
2. ステージ端に触れた敵艦は戦闘空間から消失し、撤退艦一覧に入る。撤退中の境界接触は通常の座標クランプより優先する。
3. 戦闘空間に残る敵（攻撃対象）の殲滅後、撤退艦は最も近い他の敵拠点へ0.1 AU/日で移動を開始する。「殲滅」には撃破だけでなく撤退による対象消失も含む。
4. 移動途中の再接敵時は、その遭遇戦の敵編成を一度クリアし、撤退艦一覧で上書きして生成する。
5. 移動先拠点への到達後に接敵した場合は、合流先の艦隊に撤退艦を追加して生成する。合流先の既存艦隊は消去しない。
6. 追加生成時の座標重複は、x座標を1回につき+50 Uずらし、各回で重複を再判定する。補正は最大5回（合計+250 U）。5回で解消しない場合は入力不備と同じエラー扱いとする。惑星侵入禁止領域・戦闘領域外への配置も検証する。

撤退方向への回頭中の射撃可否は未指定。座標重複の補正は合流時の追加生成に適用し、通常の入力不備を無条件で補完する規則とはしない。
