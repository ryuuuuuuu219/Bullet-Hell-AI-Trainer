# 課題追加

## 発動条件

ユーザーが新しい課題の「追加」または「新規作成」を明示的に依頼した場合に使用する。

次の依頼では使用しない。

- 既存課題の修正
- 数値調整
- バグ修正
- リファクタリング
- 課題設計についての相談
- 実装を伴わないレビュー

## 1. 追加前の定義確認

実装前に、ユーザーのプロンプトから解釈した弾幕定義を列挙する。

定義形式は、リポジトリ内の次のディレクトリを参照し、既存ファイルの形式に合わせる。

`memo/Basic設計メモ`

少なくとも次の情報を整理する。

- 課題区分
- 課題番号または追加位置
- 課題名
- 課題全体の周期
- 構成要素
- 発射元
- 発射開始時間
- 発射周期
- 1回あたりの生成数
- 発射方向および角度間隔
- 初速
- 加速度
- 角速度
- 角加速度
- 分裂条件および分裂数
- 生存時間またはプール返却条件
- 脅威度
- 予告線の有無
- その他、実装に必要な固有パラメータ

### 入力解釈規則

- 発射元はBossオブジェクトで固定する。
- 乗算記号および回数表記では、`*` と `×` の表記ゆれを同じ意味として扱う。
- `T` は課題周期の開始を0とする周期内経過時間であり、周期ごとに0へリセットする。発射時刻またはそれ以下の項目に式がある場合は、その発射時刻の `T` を式へ代入する。例えばT+8で発射する弾に `弾速200+T×5` と指定された場合、初速は240Unit/sと解釈する。
- `A第N段階` など同じ英字の段階表記は、第N-1段階の弾を発射元として第N段階を分裂生成する意味と解釈する。
- 分裂対象の限定がなければ、直前段階で生成されたすべての弾を対象とする。親を消す指定がなければ、分裂後も親を残す。
- 段階定義は、後述される分裂数、way数、角度配列、弾構造数と照合し、生成数が一致しない場合は停止して確認する。
- `○秒遅延` は分裂開始までの遅延を示す。遅延指定がなければ0秒とする。
- `○秒周期×○` は発射周期と回数を示す。`×○` がなければ回数無制限とし、`単発`は1回と解釈する。
- 線形加速度が明示されていなければ0Unit/s²とする。
- 脅威度が明示されていなければ、`memo/Basic設計メモ/脅威度ルール.txt`を読み、規則から算出する。規則から一意に算出できなければ停止して確認する。
- 予告線が明示されていなければ、予告線なしとする。

プロンプトで定義されていない項目について、既存形式または明確な既定値から一意に決められない場合は、ファイルを変更せずに停止する。

課題全体の周期が指定されていない場合は、他の値から推測せず、ファイルを変更せずに停止する。

停止時は、次をユーザーに提示する。

- 確定している定義
- 曖昧な定義
- 実装結果を変える可能性がある選択肢
- 確認が必要な質問

最後に、ユーザーがそのままコピーして値だけ追記できる「追加入力テンプレート」をコードブロックで提示する。

- テンプレートには不足または選択が必要な項目だけを含め、すでに確定している項目を再掲しない。
- 不足項目が構成要素や段階に属する場合は、対象を特定できる最小限の階層見出しを残す。
- 項目名は既存設計メモまたはユーザー入力の表記に合わせ、値は空欄にする。推測値や推奨値を記入しない。
- 複数の対象に同名の不足項目がある場合は、それぞれの階層の下へ分けて記載する。
- 選択肢の説明はテンプレートの外で行い、テンプレート自体は追加入力として成立する形式にする。

例えばA第2段階の弾速だけが不足している場合は、次の形式で返す。

```text
A第2段階：
弾速：
```

## 2. 課題区分の確認

Basic、Applied、Advanced、Finalなどの追加先区分と、追加位置をプロンプトから特定する。

次のいずれかに該当する場合は、実装せずに停止して確認する。

- 課題区分が指定されていない
- 複数の区分として解釈できる
- 課題番号または挿入位置が一意に定まらない
- 指定された区分と設計メモの構造が矛盾する

課題区分や番号を推測して追加してはならない。

## 3. 構造確認

実装前に、定義値と既存実装を照合する。

次を確認する。

- 弾速、加速度、角速度、角加速度、発射周期、分裂数、継続時間の単位
- 周辺課題と比較して極端に速い、遅い、大きい、小さい値
- 小数点、符号、桁、度とラジアン、秒とフレームの取り違え
- 未指定値が暗黙に既定値へ置き換わっていないか
- 生成数が意図せず乗算される構造になっていないか

誤字または指定ミスの可能性がある値は勝手に修正せず、疑わしい理由と比較対象を提示して確認する。

## 4. ライフサイクル確認

加速度、角加速度、時間変化、分裂のいずれかが定義されている場合、その変化が完了する前にオブジェクトがプールへ返却されないことを確認する。

原則として、次の関係を満たすことを確認する。

`最も早く成立しうるプール返却時刻 >= 最後の変化または分裂が完了する時刻`

次の返却条件を確認対象とする。

- 生存時間切れ
- 画面外または境界外への退出
- 距離制限
- 衝突
- 発射元や管理オブジェクトの終了
- 課題終了時の一括返却
- その他の自動返却条件

条件を満たさない可能性がある場合は、実装前に報告して確認する。

## 5. 負荷見込み

課題実行中に同時存在しうるオブジェクト数の最大見込みを、プールまたはPrefabの種類ごとに計算する。

計算には次を含める。

- 1回の発射数
- 発射周期
- 発射継続時間
- 各オブジェクトの最大生存時間
- 複数発射元
- 全方位複製
- 時間差発射
- 分裂前の親オブジェクト
- 分裂後の子オブジェクト
- 複数構成要素の重複期間
- 予告線、レーザー、エフェクトなど別プールのオブジェクト

各プールについて、次を報告する。

- 初期プール数
- 最大同時存在数の見込み
- 初期プール数との差
- 不足時の追加生成数の見込み
- 計算上の前提
- 厳密値を出せない場合は安全側の上限

初期プール数を超える場合でも、ユーザーの指定なしに値を変更しない。必要数と変更候補を報告する。

## 6. 実装とテスト

定義と追加位置が確定した場合のみ実装する。

実装後は、プロジェクトで利用可能なコンパイルまたはテスト手段を実行し、少なくとも次を確認する。

- コンパイルエラーがない
- 実行したテストでエラーがない
- 新規課題が指定された区分と位置に登録されている
- 必要なPrefab、プール、参照が欠落していない

テストを実行できない場合は、実行したと偽らず、実行できなかった理由と未確認項目を明記する。

## 7. 設計メモへの反映

実装とテスト確認が完了した後、次のディレクトリにある該当ファイルへ新規課題の定義を追記する。

`memo/Basic設計メモ`

既存ファイルの記載形式、並び順、単位、用語に合わせる。

実装に失敗した場合や定義が未確定の場合は、確定済みの課題として設計メモへ追記しない。

## 完了報告

次をまとめて報告する。

- 追加した課題と追加位置
- 実装した弾幕定義
- 構造確認で検出した注意点
- 最大同時オブジェクト数の見込み
- 初期プール数との比較
- 実行したテストと結果
- 更新した設計メモ
- 残っている未確認事項
